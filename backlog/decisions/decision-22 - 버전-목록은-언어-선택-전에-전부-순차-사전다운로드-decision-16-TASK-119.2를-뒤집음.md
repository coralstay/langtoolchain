## Context

TASK-163~168로 companion(pnpm/uv) 버전 프롬프트가 목록을 못 보여주는
문제를 조사한 결과: pnpm(1.88MB)/uv(9.65MB) 목록 응답이 다른 플러그인
(nodejs 331KB 등)보다 4~23배 큰데도 공통 5초 타임아웃(LT_VERSION_
FETCH_TIMEOUT)을 그대로 쓰고, uv는 런당 GitHub API를 2번(latest+list)
호출해 시간당 60회 비로그인 제한을 쉽게 소진하며, decision-17의
서킷브레이커(한 플러그인이라도 fetch 실패하면 그 세션 나머지 전부
즉시 실패 처리)가 부모보다 늦게 물어보는 companion에 불리하게 작용함을
확인했다. TASK-169에서 타임아웃 확대(LT_LARGE_LIST_TIMEOUT)와 uv API
호출 절반 축소(latest를 list의 첫 항목으로 대체)는 별도로 적용했지만,
그것만으로는 "부모가 먼저 실패하면 나중에 물어보는 companion이 이유도
모른 채 정적 기본값만 뜨는" 근본 구조(어떤 플러그인이 먼저 질문받고
먼저 fetch되는지에 따라 실패가 조용히 전파되는 것)는 그대로 남는다.

decision-16(TASK-128.3)과 TASK-119.2는 "조회는 lazy(선택 시점), 거절할
언어는 fetch 안 함"을 명시적으로 채택한 바 있다 - "이미 답하고 있는
프롬프트 옆에서 기다리는 건 체감이 안 되고, 어차피 거절할 언어를 미리
fetch하는 건 낭비"라는 논리였다.

## Decision

00_select.sh가 언어 선택 질문을 시작하기 전에, `.tool-versions`에 있는
8개 플러그인(언어 5개 + companion 3개) 전부의 버전 목록을 순서대로
미리 fetch해서 캐시(LT_VERSION_LIST_CACHE_FILE)를 채운다. "버전 정보
가져오는 중..." 한 줄을 보여준다. decision-16/TASK-119.2의 "lazy,
거절할 언어는 안 가져옴" 방침을 이걸로 뒤집는다 - 사전다운로드는 사용자가
나중에 거절할 언어의 목록까지 항상 가져온다.

병렬 백그라운드 프리페치(체감 지연 거의 없음)도 검토했으나, 여러
프로세스가 같은 캐시 파일을 동시에 읽고-고치고-쓰면 경쟁 상태로 캐시가
깨질 위험이 있고 이를 막으려면 락 처리가 추가로 필요해 순차 방식으로
확정했다(사용자 확인, 2026-09-20).

서킷브레이커(decision-17) 설계 자체는 안 건드린다 - 사전다운로드 중
하나가 실패해도 그 세션의 나머지는 여전히 조용히 스킵된다. 이 decision이
바꾸는 건 "그 실패가 언제 보이는가"뿐이다: 지금까지는 인터랙티브 흐름
중간에 어떤 companion의 메뉴가 뜬금없이 비어 보이는 방식으로 나타났다면,
이제는 첫 질문이 뜨기도 전에 "버전 정보 가져오는 중..." 단계에서 실패
메시지가 먼저 보인다.

## Consequences

- 사용자가 모든 언어를 거절해도(모두 No) 8개 플러그인 목록을 전부
  fetch한 뒤에야 첫 질문이 뜬다 - TASK-119.2가 피하려던 정확히 그
  낭비다. 트레이드오프로 받아들인다: companion이 원인 불명으로 실패해
  보이는 문제가 이 낭비보다 더 큰 사용자 혼란이라고 판단.
- 설치 시작까지의 체감 대기시간이 늘어난다(8개 fetch 합산 시간).
  LT_LARGE_LIST_TIMEOUT 확대와 맞물려 최악의 경우(pnpm/uv가 느릴 때)
  기존보다 대기가 더 길어질 수 있다.
- decision-16이 분리해둔 "단일값 캐시"와 "목록 캐시"는 이 사전다운로드가
  목록 캐시만 채우므로 그대로 유지된다 - lt_resolve_default_version()이
  단일값을 다시 조회할 때(uv는 TASK-169로 목록 캐시를 재사용하도록
  바뀜) 대부분 캐시 히트가 된다.
